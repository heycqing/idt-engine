# 调查：拓扑边为什么稀疏

> 日期：2026-10-22
>
> 宿主：`trade-monorepo` / 财达（`apps/caida`），拓扑基线 110 条路由
>
> 性质：只读调查，不含改动

## 问题

财达 110 条路由里只有 23 条有出边，共 33 条边。跨页流程基本编不出来，而跨页正是 IDT 的核心价值。

## 不是什么

先排除两个一开始以为的原因。

**不是命名路由。** 假设是 Vue 常见的 `$router.push({ name: 'Foo' })` 写法提取器不认。实测财达 174 处跳转调用里，用 `{ name: ... }` 的**一处都没有**。这个假设完全不成立。

**不是目标解析不了。** 能抽出字面量目标的 94 处调用里，96.8% 的目标就是拓扑里的已知路由。目标侧没有问题。

## 真正的原因：跳转写在子组件里，而提取器只认页面文件

174 处 `$router.push/replace/go/back` 的参数形态：

| 形态 | 数量 | 占比 | 可提取 |
| --- | ---: | ---: | --- |
| `{ path: '字面量' }` | 63 | 36.2% | 是 |
| `'字面量'` | 31 | 17.8% | 是 |
| 变量 / 表达式 | 28 | 16.1% | 否 |
| `go()` / `back()` | 23 | 13.2% | 无目标，不该算边 |
| `{ path: 变量 }` | 20 | 11.5% | 否 |
| 对象里既无 name 也无 path | 9 | 5.2% | 否 |

能提取的是 94 处（54%）。但这 94 处所在的文件：

| 位置 | 数量 | 占比 |
| --- | ---: | ---: |
| 页面文件自身 | 37 | 39.4% |
| 子组件（`*/components/*`） | 34 | 36.2% |
| `service/` 与 `utils/` | 12 | 12.8% |
| 其他非页面文件 | 8 | 8.5% |
| `App.vue` | 3 | 3.2% |

**只有 39% 落在页面文件里**，其余 61% 写在子组件和公共模块中。提取器把跳转挂到页面节点上，所以这 61% 全部丢失。37 处页面内调用去重后正好对应现在的 33 条边、23 个页面。

## 顺 import 图能拿回多少

从每个页面出发做 import 闭包（跳过其他页面文件，避免把别的页面的跳转算进来），按最大深度统计：

| 范围 | 有出边页面 | 边数 | 单页最多 |
| --- | ---: | ---: | ---: |
| 现状（只看页面文件自身） | 23 | 33 | — |
| 深度 1（直接子组件） | 75 | 255 | 9 |
| 深度 2 | 80 | 341 | 14 |
| 深度 3 | 80 | 920 | 19 |
| 不限深度 | 80 | 1348 | — |

**深度 1 的性价比最高**：有出边的页面从 23 涨到 75（占 110 条路由的 68%），边数 33 → 255，单页最多 9 条边，图仍然稀疏可用。

深度 2 只多 5 个页面、86 条边，收益有限但还算克制。

深度 3 开始失控：页面数不再增长，边数却多出 579 条——这是 `utils/`、`service/` 这类公共模块被每个页面的闭包吃进去造成的污染。不限深度时 1348 条边摊到 80 个页面约等于每页 17 条，图近乎全连通，寻径会失去意义。

## 建议

跟 import 图走，**深度限 1，默认不跨公共模块**。深度 2 作为可选项留给标志。

需要一并想清楚的，不只是"多拿多少条边"：

- **触发文本从哪来。** 现在 `triggerElementText` 取自同一个 SFC 的 click 映射。跳转移到子组件之后，触发它的按钮文本在组件自己的模板里，提取器要一并扫，否则边有了但 IDT 不知道点哪里。
- **精度会下降。** 组件被页面引入不等于页面 UI 上真能走到那条跳转（可能在条件分支里）。错边不会悄悄污染数据——它只会让生成的 spec 在运行时失败，但会浪费一次模型调用和一次跑测试。
- **`go()`/`back()` 这 23 处不该当边**，它们没有确定目标，当前也确实没被算进去，保持现状。
- **16% 的变量跳转仍然拿不到**，这部分静态分析到此为止，不必追。

## 下一步

这份调查支持写一份设计文档：《按 import 图归属跳转》。核心决策点是深度上限、公共模块的排除规则，以及触发文本的来源。
